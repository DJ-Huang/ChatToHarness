# ADR: Optional Windows computer use service

Date: 2026-10-19 (Asia/Shanghai)
Status: source preview, requested by the user; native application compatibility remains subject to acceptance

Use the existing third-party MCP route rather than add an unrestricted built-in tool. The service exposes a single strictly validated action interface and a fixed native helper, launched with shell:false and an environment allowlist. Existing application trust/per-tool permission remains in force; an additional native picker binds every session to one locally selected window. Never change allowed directories, shell policy or arbitrary process termination to enable this capability.

Inputs require a recent one-use observation, unchanged outer-window geometry and foreground target. The helper verifies the window's owner PID and process start time, rejects minimized/unavailable windows and checks occlusion for pointer actions. Input batches are bounded, serialized and never replayed. Stop is out-of-band via a local window/hotkey; sessions expire and the helper watches its owner. The only termination is of this service's own helper.

PrintWindow avoids falling back to arbitrary screen capture but is not reliable for every application. SendInput uses global OS routing, so foreground checks cannot eliminate all races. Window authorization does not confine file/network effects. This is deliberately not called a sandbox. Higher integrity/UAC/secure desktop support, UI Automation selectors, arbitrary hotkeys, clipboard reads, full desktop access, browser-specific drivers, automatic installation and cross-platform support are outside the initial scope. The selected-window consent does not approve future effects independently of user intent.

No screenshot/title/text persistence is introduced. The standalone source service integrates through existing MCP settings; installer integration can follow after native acceptance and platform packaging review.

2026-10-20: Local Windows builds now bundle the optional standalone service and its production dependencies. Neither installation nor config generation enables trust or tool permission. Package relocation, production consent and local STOP/hotkey passed fixture acceptance; actual NSIS install/uninstall remains gated on a dedicated CI profile. Published release assets are unchanged.

2026-10-20 user-requested revision: default authorization is now `all_windows`, with `per_window` available through the service startup configuration `CTH_COMPUTER_USE_AUTHORIZATION_MODE`. The default change and broad window enumeration are explicitly requested by the user, rather than inferred from folder access or tool annotations. Tool calls cannot change this mode. Global mode permits listing visible targets and selecting one without a picker; scoped mode requires local consent for each new session and refuses remote window enumeration. Neither changes shell policy, allowed directories, PID termination or OS privileges.

Opening now returns a routing ID before consent/initialization. `get_session` and repeated open recover the same session without replaying input; an ID-less close releases only this configured service's current session. All clients with permission to this service already share a single local session; IDs are not an independent authorization boundary. No automatic retry of input is introduced. Explicit close can cancel busy native input, and old completion callbacks cannot clear a new session. Structured output and text both carry the routing ID; startup failures remain queryable.

2026-10-20 focus/image revision, explicitly requested by the user: `activate` restores only the session's bound window and verifies foreground after bounded attempts. Identity checks precede activation; input remains separately guarded and requires a fresh observation. The fallback temporarily attaches the helper UI thread's input queue to foreground/target threads with unconditional detachment. It does not change foreground-lock settings or inject fake keystrokes/clicks. Windows can deny activation, which is reported rather than assumed successful. See Microsoft's [SetForegroundWindow restrictions](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setforegroundwindow) and [AttachThreadInput behavior](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-attachthreadinput). A hung target can still cause the native operation to time out; only the owned helper is terminated.

Observe now returns matching PNG bytes in native image content and a typed structured fallback. No new screenshot persistence, HTTP endpoint or directory grants are introduced. PNG size is reduced to 2 MiB to fit the duplicate representations under the existing gateway budget. SHA-256 and byte length let clients verify decoded bytes; these checks do not establish that captured pixels are visually correct. Real remote-client rendering remains separately unverified.

2026-10-20 compression/chunk revision supersedes the preceding 2 MiB rejection. Native PNG is bounded at 40 MiB (within the existing 8-megapixel guard), with a separate 64 MiB local helper JSON bound. It never sends that payload through the network gateway. Pinned sharp 0.35.5 compares optimized PNG with lossless WebP at original resolution; the smaller encoding wins, with an explicit PNG compatibility option. The choice follows [sharp's encoder options](https://sharp.pixelplumbing.com/api-output/) and [WebP's lossless design](https://developers.google.com/speed/webp/docs/compression); no universal codec superiority is assumed. Lossy compression is deliberately avoided for UI text.

Compressed images above 1 MiB become an opaque snapshot manifest. `read_screenshot` returns bounded byte ranges (default 256 KiB, max 512 KiB) with per-chunk and whole-image hashes. Reads are repeatable, bound to the current session and screenshot ID, and do not extend input authorization. Only one compressed snapshot is cached, automatically released after 120 seconds or on refresh/activation/input/close. Client-side assembly must decode each chunk before concatenating. The network gateway's 8 MiB bound is unchanged. Existing trusted clients already share this single service session; IDs are routing handles. No persistence, shell permission or folder grant changes occur. Native sharp/libvips binaries and their upstream licenses must travel with the optional service.
