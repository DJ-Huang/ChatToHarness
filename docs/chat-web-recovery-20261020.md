## 本地代理是否有关

系统 HTTP、HTTPS、SOCKS 代理均为 `127.0.0.1:7897`，另有 TUN 路由。`cdn.platform.openai.com` 的 DNS 地址为 `198.18.0.156`，出口接口为 `utun1024`。Clash Verge 可见连接中，主站匹配 `DomainSuffix(chatgpt.com)`，显示资源匹配 `DomainSuffix(openai.com)`，均走 `AI → Proxies → USA 02`；未观察到显示资源被误分流到直连。

因此流量确实经过本地代理，但本次恢复没有切换代理、关闭 TUN、修改规则或调整安全设置。现有证据不足以将故障归因于代理，也不能保证该节点在所有时段都稳定。具体配置证据保存在 `recovery/proxy-evidence.json`。

## 将答案生成与页面显示分开验证

一次不调用工具、只要求回复 `OK` 的请求中：

- `backend-api/f/conversation` 返回 HTTP 200，约 2.54 秒；EventStream 实际包含助手文本 `OK`、`finished_successfully`、`end_turn:true` 和 `[DONE]`。
- 同页 `https://cdn.platform.openai.com/deployments/dil/v14/runner.html` 在 10 秒处失败，接收 0 字节。页面显示“无法加载此回复”。
- 随后独立打开相同公开资源，页面标题为 `DIL Runner`，可以加载。

这将该次失败定位到完整答案生成之后的显示路径。它不是“本地写出成功”的推断，也不是仅凭 HTTP 200 判定云端完成。证据为 `recovery/stream-proof.json` 及 `stream-completed-runner-failed.png`。独立打开成功也不能证明当时嵌入该资源的整个链路无故障。

## 调试连接与重载的对照

保持相同代理，观察到以下顺序：

| 操作与条件 | 网页结果 |
|---|---|
| 断开浏览器调试连接，使用原生 Edge 输入 | 纯文字 `OK` 可见 |
| 重新附加调试连接，复用已经加载的页面并用原生输入 | 第二个 `OK` 仍可见 |
| 调试连接附加时重载页面 | 同样两个已保存答案均变成“无法加载此回复” |
| 断开调试连接，从普通 Edge 菜单刷新 | 同样两个答案再次显示为 `OK` |

可复现的关联是**附加调试连接时重载页面**与显示失败。单纯附加连接并不一定失败，尚未确认调试协议内部的具体原因。此前还做过授权缓存清理及直接打开显示资源，不能把整个恢复过程归功于单项干预。

最终插件验收只使用原生 Edge 操作和观察，没有再次附加浏览器调试连接。若出现同样错误且顶部显示浏览器正在被调试，可先结束该调试连接，再从普通 Edge 刷新。此操作没有修改浏览器安全、权限或代理配置。

对照证据：`recovery/debugger-control.json`、`native-detached-ok.png`、`reattached-reload-failed.png`、`detached-reload-ok.png`。早期纯文字对照发送时的模型未完整记录，不作为固定模型性能对照；最终三项插件验收已另行确认模型。
