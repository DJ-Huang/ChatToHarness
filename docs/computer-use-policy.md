# Computer Use 操作规范（规范源）

状态：生效，适用于 ChatToHarness 的 macHarness / winHarness Computer Use 及代理选择工具的行为。其他入口需要显式引用本文件；不能仅凭仓库文档保证 ChatGPT 客户端遵守。

## 0. 双平台持续恢复（Windows / macOS）

只要用户没有通过 STOP/Esc、明确文字指令终止 Computer Use，且原会话仍有效，就不得因单次错误放弃整个任务。调用端应持续检查会话、目标身份、前台、输入状态和最新观察并继续，直到结果已核验、用户主动停止或会话终止；可恢复错误没有固定重试次数上限。

- CU_WINDOW_NOT_FOREGROUND：重新激活目标、重新观察、从未完成步骤继续。
- CU_USER_INPUT_ACTIVE：表示存在输入冲突，不等于用户要求停止。暂停合成输入，确认按键/鼠标释放后重新观察并恢复。用户接管期间不得争抢控制。
- 遮挡、截图过期、位置变化及临时错误：重新确认目标、读取实际状态、计算安全后续操作。结果未知时不得盲目重放点击、输入或拖动。
- 保留原生输入保护、左键释放、权限限制与 STOP/Esc。会话被主动停止或已结束后不得私自重建，也不能绕过安全保护。完成任务后必须 close_session。
- 此规则同时约束 Windows 与 macOS。对于**任意已授权 GUI 任务**，统一通过 `start_task`/`get_task`/`cancel_task` 管理生命周期，通过可信 Planner 动态选择下一步；如果没有决策服务则进入 `awaiting_decision` 并通过 `submit_task_decision` 接收调用端的单步决策。`start_move_task` 是兼容接口和专项验收用例，不再代表总体架构。步骤只保存无截图检查点；配置有持续运行的可信 Planner 才可本地自动逐步决策。未配置 Planner 时，调用端需针对每个待决策观察主动提交下一步。进程/原会话终止后不能凭检查点重新注入输入，必须重新授权并创建新任务；其它任意 GUI 规划仍需上层调用端驱动，不等于后台自主模型代理。

## 1. 默认操作方式：可见的真实输入

用户要求点击、输入、移动窗口、拖动窗口、调整桌面 UI 等**图形交互**时，默认调用所选设备的 `computer_use`，并使用真实鼠标与键盘事件。窗口拖动采用：

1. `observe`：确认前台目标、窗口 ID、标题栏、显示器坐标及授权。
2. `mouse_move`：将系统真实指针移动至可拖动标题栏。
3. `mouse_down`：按下左键并保持。
4. `observe`：取得新鲜观察。
5. `mouse_drag`：按住左键，沿相连显示器实际路径移动。
6. `mouse_up`：释放鼠标；即使拖动改变窗口坐标，也应能执行释放。
7. 使用观察/系统只读查询核对位置及用户要求的前台状态。
8. **结束前必须调用 `close_session` 并确认 `closed: true`，然后才能向用户回复“已完成”**。无论成功、失败或用户中止，都需尽力关闭当前会话。只调用 `mouse_up` 不会关闭 STOP/Esc 面板，不能把主任务完成等同于会话退出。

禁止仅为加快执行而**静默改用** AppleScript、Accessibility `AXUIElementSetAttributeValue(kAXPositionAttribute)`、Win32 `SetWindowPos` / `MoveWindow`、shell 脚本或其他不可见的系统级定位手段。系统只读检查、开发编译、诊断、测试不受该限制。

### 双平台原子拖动与遮挡恢复（macOS 0.7.3、Windows 同仓库源码）

- Windows 和 macOS 移动窗口优先使用 drag_window，在一次调用中用新鲜 observation 的 x,y 标题栏位置和 screen_x/screen_y 完成真实鼠标移动、按下、拖动、松开。Mac 使用 Quartz 点坐标；Windows 使用虚拟桌面物理像素。无需跨多次 MCP 往返保持左键。未经允许仍不得调用 setpos。
- observe 额外报告 window_bounds 和 desktop_displays，按此计算目标光标终点，移动后再次观察核验。
- 原子拖动只在尚未按下鼠标前对初始标题栏及最多两个备选落点做只读遮挡检测（最多三处）。备选落点变化时同步补偿终点，最终窗口位置不变。已经发送按下/拖动后绝不自动重放。
- CU_TARGET_OCCLUDED 返回 occlusion 元数据，不返回其它窗口标题。Mac 含窗口 ID/PID/进程名/层级/透明度/边界/AX 检查状态；Windows 使用 WindowFromPoint 命中检测并返回窗口 ID/PID/进程名/边界、hit_test 标识。两端遇到无法确认的命中均应保守拒绝，不得仅凭透明度假定能穿透。
- **激活后仍被遮挡的窗口恢复**：如果 `activate` 已确认目标在前台，但后续点击或截图仍显示 `CU_TARGET_OCCLUDED`，不要直接认定任务失败。先 `get_session` / 重新 `observe`，核对目标窗口 ID/PID、实际遮挡区域及用户是否在操作；必要时调整本工具 HUD 位置或改用目标窗口内可见的安全落点。若仍无法访问原操作控件，且**目标窗口标题栏存在可见、可安全拖动的区域**，可考虑将**同一已授权目标窗口**临时移至当前显示器的可见区域：优先使用 Computer Use 的真实 `drag_window`（或受支持的分步鼠标拖动），保持窗口尺寸，不移动遮挡方或其他应用窗口；拖动后重新激活、观察并核验位置，再继续原任务，条件允许时可恢复原位置。任何拖动前均要确认无遮挡的标题栏落点、有效会话和安全目标位置；若标题栏也完全不可达、命中测试不确定、用户接管或 STOP/Esc 已触发，不得绕过保护，也不得借此启用未授权的 AppleScript/Accessibility/Win32 直接定位。若发生不确定的输入结果，先核验实际位置及左键释放，不得盲目重放。
- 三处均被遮挡、出现 CU_POINTER_OFF_PATH、焦点变化、身份变化或不确定输入时，先检查会话和重新观察，必要时重新激活；不得盲目重复原动作。Windows 原子拖动在尚未注入鼠标动作的确定性遮挡失败时报告 `not_started` 且允许重新观察；输入结果不确定则须关闭会话。Windows HUD 若遮挡目标标题栏，应移至同屏安全位置，不得让 HUD 造成自遮挡。Esc/STOP、旧分步接口 30 秒 watchdog 和 close_session 保留。

## 2. 直接定位 API 兜底（已取得针对当前窗口任务的授权）

用户在 2026-10-22 明确允许：当真实鼠标拖动无法完成 ChatToHarness 窗口移动时，可以考虑系统 API，而不是放弃任务。这是对已授权目标窗口的有条件兜底，不是对任何设备、窗口及操作类型的无条件许可。

### 窗口移动任务的分级恢复

1. **真实输入优先**：Windows 和 macOS 都优先 Computer Use 的 drag_window；出现遮挡时重新观察、激活并在按下前试最多三个安全标题栏落点。不对未知执行结果自动重放。
2. **判断能否回退**：如果真实鼠标仍失败，核对会话、目标 PID/窗口 ID、前后台状态、屏幕排列和是否有按住的鼠标。**权限拒绝、Esc/STOP、用户接管、身份不明、设备不匹配时必须停止，不能用 API 绕过。**
3. **受控 API**：在当前用户明确允许的目标范围内优先使用独立授权的专用窗口定位能力；如无此能力，可在已授权本地环境使用 macOS Accessibility AXUIElementSetAttributeValue(kAXPositionAttribute) 或 Windows SetWindowPos，仅移动该目标窗口。使用命令执行通道的最小化脚本时，必须绑定到该窗口 PID/ID，明确向用户告知实际采用的 API，不得暗中切换，不能把脚本操作冒充成真实鼠标拖动；不包括任意其它 GUI 操作、权限提升、修改其它窗口或回避 STOP/Esc。
4. **核验位置**：读取目标窗口和显示器当前矩形，计算贴边、上下居中等目标位置；API 完成后用独立只读查询复验窗口 ID、位置及尺寸，不得仅凭 API 返回成功作为验收。若未达标，重新判断原因，禁止未知执行状态下的无条件重复。
5. **清理和审计**：进入 API 前先释放可能按住的鼠标，关闭原 Computer Use 会话并核验 closed:true。最终报告真实鼠标操作与 API 瞬间定位的区别、采用原因、目标与最终实测坐标。

只有用户明确允许直接设置坐标、精确定位或 API 失败兜底时才能使用上述定位方式；无授权或无法安全验证时，应报告具体原因。

## 3. 多设备选择（当前规则）

ChatGPT 会话根据已连接工具的设备标题/元数据确定设备，用户**不需要输入 UUID**。决策优先级如下：

1. **明确指定优先**：用户本次指明具体电脑、设备名称或可唯一匹配的 Mac/Windows 时，选择该设备，即使当前会话已经关联别的设备。找不到或匹配多个时，不得回退到其他设备。
2. **会话关联优先于数量**：若用户没有另外指定设备，且当前 ChatGPT 会话已**可信地关联**到某个可用 Harness 设备，默认直接操作这一台；即使还有其他 Harness 同时连接也不再询问。
3. **只有一台可用设备**：会话没有关联设备且只有一台 Computer Use 设备可用时，自动使用它。
4. **无法自动判断时选择**：会话没有可信关联，且候选设备多于一台，按稳定顺序呈现 `1、2、3…` 编号、友好设备名称和系统类型，请用户选数字。不能根据设备列表顺序、操作系统或最近使用的工具擅自猜测；不得向用户显示或要求输入内部 UUID。

“当前会话对应的设备”仅指由 ChatGPT/可信路由层提供的**当前对话设备绑定**。本地 Harness 自己的设备 ID、当前前台应用、工具所在电脑或一次历史操作均不能自动证明当前对话已绑定该设备。绑定设备掉线或用户明确指向的设备不可用时不静默故障转移，应重新列出当前可用设备或报告不可用。

工具层 `_meta["com.chattoharness/device"]` 上报设备 ID/名称/平台，`target_device_id` 保持可选且仅用于校验显式提供的 ID。所选 Harness 自动绑定自己的设备 ID，操作仍需独立通过操作系统权限、窗口作用域、Esc/STOP 及新鲜截图验证。

## 4. 参数与生命周期约束

- `mouse_down` 必须含新鲜的 `observation_id` 和窗口截图 `x,y`；`mouse_up` 只需要 `session_id`。两者均支持可选 `button: left`；拖拽不支持 `right`。
- GUI 任务完成后，无论最终窗口位置是否已验证，必须独立 `close_session`；关闭响应和用户任务结论必须分开核验。服务内另有 **120 秒无调用自动关闭**兜底，但它不替代任务级显式关闭。

### 会话标题和可见操作状态

- Windows/macOS 调用 `open_session` 时 AI **必须传入可读的 `session_title`**（建议直接描述当前授权任务，如“验证记事本自动输入”）。仅在实际可获取 ChatGPT/Codex 对话标题时才能使用其原文；无法获取时以真实任务描述命名，禁止使用 GUID、设备 ID、猜测的会话标题。缺失名称直接拒绝创建会话。原生 UUID 仅供内部关联和诊断。
- 会话标题必须是 1–80 字符的非控制文本；只通过已授权会话的本地原生 stdio 设置，不拼入辅助进程命令行/环境变量，原生程序不主动将标题记录到日志。不接受在其它动作上传标题，也不允许隐式伪造 ChatGPT/Codex 来源。
- HUD 两行分别表示“当前”（仅当前实际执行的原生动作，执行完后回到等待）与“上一步”（最近一次执行完成/失败的原生动作 + 结束时间）。不能称“等待下一步”为正在执行中的动作；不能把输入文字、按键内容、截图或其它敏感参数显示到浮层。MCP 层预检失败且未到达本地原生程序的动作，不显示成已经执行。

## 5. 输入异常及替代方式

- Windows 与 macOS 的可恢复操作失败须按第 0 节持续诊断并继续任务，不得直接放弃。真实用户接管期间暂停注入；用户主动 STOP/Esc、明确停止、权限撤销或会话终止时必须停止，禁止切换设备或用系统 API 绕过权限和停止机制。
- 出现不确定的输入结果时不得盲目重放；保证合成按键/鼠标在中止时释放。
- 真实鼠标路径应可观察；不得将瞬间窗口跳转描述为真实拖动。

## 6. 结果证据

每次 GUI 操作报告应区分真实鼠标/键盘、系统 API 直接调用、模拟测试、真实桌面验收。位置、尺寸与前台状态以操作后验证为准；不能用命令成功的返回值替代最终状态核验。

## 7. 工具与实施边界

- 以本文件为仓库规范源；根目录 `AGENTS.md` 引用本文件；原生 Computer Use 工具描述及命令执行工具说明包含关键约束。
- 设备优先级在 `app/computer-use-devices.cjs` 的**纯路由规则**中可测试。但独立 Harness **无法枚举整个 ChatGPT 会话关联和所有连接**；真正的跨工具路由由 ChatGPT 客户端/可信聚合层执行。纯路由规则不会凭空建立会话绑定。
- `start_process` / `start_task` 等任意命令执行能力仍可调用操作系统窗口 API。文本提示不能严格阻止恶意或错误的替代行为；若需技术级强制隔离，必须进一步实现可信的会话级能力网关或系统级权限边界，同时不破坏开发编译/诊断功能。
- 此操作规范不得绕过任何既有安全和授权机制。

## 8. 2026-10-23 双平台 Computer Use 操作与 HUD 回归要求

- **首次截图前必须确认前台**：会话获得授权、原生 helper ready 后先执行 activate。激活因用户输入而失败时不抢焦点，get_session.next_action=activate；恢复后再允许首张 observe。任务管理器同样先激活再观察。
- **原子拖动**：新鲜观察、唯一授权窗口的标题栏安全落点，顺序为真实鼠标可见移动、按下左键、拖至目标屏幕坐标、确认释放、重新截图验证。不得将系统定位 API 冒充拖动；不得无观察重放不确定动作。
- **指针偏移不是取消**：Windows 不再以离轨 6 像素作为硬中止；短暂偏移时等待指针稳定，基于实际位置重新规划。用户持续操作、按住非自动化按键/按钮时不得抢夺；有界本地等待后返回可恢复冲突，由原任务循环再观察。按下左键后只有确认原生释放成功才保留会话；无法确认则安全终止。用户 STOP/Esc 始终优先。
- **辉光与授权分离**：会话生效期间，真实鼠标辉光穿过整个桌面；输入授权仍严格限制于当前目标窗口。
- **HUD 身份信息**：session_title 是任务描述；宿主提供或用户明确告知确切 ChatGPT/Codex 当前对话名称时，调用端必须通过 conversation_title 传入原文；未知时明确显示“未提供”而不是任务名。会话复用时若补充或更正名称，必须更新原会话 HUD，不能静默丢弃；原生动作或任务执行中返回可恢复忙碌状态，待空闲后更新，不重建授权会话。始终显示目标窗口标题、PID、当前任务阶段、上一操作与 STOP/Esc。STOP 需圆角且不遮挡外侧流动描边。
- **规划执行边界**：确定的窗口拖动原子执行；任意 GUI 任务使用同一会话 start_task/get_task/submit_task_decision 的观察-决策-执行-验证循环。没有可信 Planner 就进入 awaiting_decision，不能声称完全自主。
- **任务 ID 发布门槛**：对外 MCP Schema 的 task_id 正则与设备 ID + 13 位毫秒时间戳保持一致，真实 MCP SDK→Gateway→native 路由必须通过 start_task→get_task→submit_task_decision→succeeded→closed。客户端缓存旧 Schema 时要求刷新/重新连接。
